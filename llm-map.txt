## Project Identity

- **Name**: Gherkio
- **Tagline**: Declarative Integration Testing Platform
- **Language**: Go 1.25.0
- **Module**: `github.com/muhfaris/gherkio`
- **Author**: Faris (muhfaris)
- **License**: Not yet specified

### What Gherkio Is

A CLI tool that executes declarative YAML-based integration test scenarios against HTTP APIs. Users describe requests, assertions, and variable extractions in YAML — no imperative code required.

### What Gherkio Is NOT

- A general-purpose programming language
- A unit testing framework
- A browser/E2E testing tool
- A BDD/Gherkin natural language parser

## Architecture & Data Flow

### Execution Flow (`runner.Run()`)

```
Load YAML test file  ──→  Load environment YAML  ──→  For each phase:
    │
    ├── Setup (if defined)
    │   └── 1. Execute setup steps (failure skips main steps, teardown still runs)
    │
    ├── Steps (if setup succeeded)
    │   ├── 1. Interpolate request variables ($var / ${var})
    │   ├── 2. Resolve URL (via env.baseUrl or env.services[].baseUrl)
    │   ├── 3. Execute HTTP request (Wrapped in Retry Loop if `retry` is configured)
    │   ├── 4. Auto-decode JWT from response.token or response.access_token
    │   ├── 5. Run assertions (status + body/JWT matchers)
    │   ├── 6. Extract & save variables (on successful retry or after exhaust)
    │   └── 7. Collect results
    │
    └── Teardown (if defined)
        └── 1. Execute teardown steps (always, even if setup/steps failed)
            - Failures are recorded but don't affect scenario pass/fail
```

## Key Design Patterns & Conventions

### 1. Cobra CLI Pattern

- Root command in `cmd/root.go`
- Subcommands in `cmd/<name>.go` with `init()` registering via `rootCmd.AddCommand()`
- Each subcommand's `RunE` calls a private function (e.g. `runInit()`, `runTest()`)

### 2. Explicit Error Handling

- All errors are wrapped with `fmt.Errorf("context: %w", err)` 
- No panics in production paths
- CLI commands return errors (not `os.Exit`) so cobra handles exit codes

### 3. YAML Model Pattern

- Models use `yaml` struct tags
- `Expect` has a custom `UnmarshalYAML` to handle mixed-type inline fields:
  - `status` → integer field
  - Everything else → `map[string]interface{}` via `,inline`

### 4. Path Syntax (Canonical)

Assertion and save paths follow dot-notation:

| Prefix | Context | Description |
|--------|---------|-------------|
| `body.<field>` | expect / save | Response JSON body field (canonical) |
| `headers.<name>` | expect / save | Response header |
| `status` | expect only | HTTP status code |
| `jwt.<claim>` | expect / save | Decoded JWT claim (auto-decoded from `body.token` or `body.accessToken`) |
| `timing.max` | auto (from `timing:` block) | Step duration must be ≤ max (e.g. `500ms`, `1s`) |
| `schema` | expect only | Validates full parsed response body against a YAML schema |

**Backward-compatible aliases** (still work but not recommended for new tests):
- `response.<field>` → same as `body.<field>`
- `response.body.<field>` → same as `body.<field>`
- `response.headers.<name>` → same as `headers.<name>`
- Bare `<field>` → fallback, tries response body directly

**Rule of thumb:** In expect, use `body.X`. In save, use `body.X`. Always explicit, never ambiguous.

### 5. Matchers

| Matcher | Behavior |
|---------|----------|
| `exists` | Field must exist (any value) |
| `not exists` | Field must NOT be present (negative assertion) |
| `uuid` | Valid UUID format (v4) |
| `email` | Valid email format |
| `datetime` | Valid RFC3339 / ISO8601 datetime |
| `uri` | Valid URI format (e.g. https://...) |
| `string` | Value is a string type |
| `number` | Value is a numeric type (int, float, json.Number) |
| `boolean` | Value is a boolean type |
| `array` | Value is an array type |
| `object` | Value is an object type (map) |
| `null` | Value is null |
| `true` | Value is boolean true |
| `false` | Value is boolean false |
| `contains <substring>` | String contains substring (case-sensitive) |
| `startsWith <prefix>` | String starts with prefix |
| `endsWith <suffix>` | String ends with suffix |
| `regex <pattern>` | String matches regex pattern |
| `count(path): <N>` | Array has exactly N items (collection matcher) |
| `all(path): <matcher>` | Every element in array matches (collection matcher) |
| Literal value (e.g. `admin`, `200`) | Equality comparison (string) |
| `schema: <name>` | Validate full response body against a YAML schema |
| `schema: not <name>` | Response must NOT match schema (negative assertion) |

### 6. Variable Interpolation

- Syntax: `$var` or `${var}` or `${var:default}`
- Applied to: URL, headers, body (recursive string/map/array)
- See `internal/runner/interpolator.go`
- Variables are stored in `map[string]interface{}` and passed between steps

### 7. JWT Auto-Decoding

If `response.token` or `response.access_token` exists and is a string, it's automatically decoded (no signature verification) into a `map[string]interface{}` available via `jwt.<claim>` assertions.

### 8. Sensitive Field Masking

When displaying request/response bodies in the console, sensitive field values are automatically masked as `***masked***`.

**Built-in default fields:** `token`, `accessToken`, `access_token`, `refreshToken`, `refresh_token`, `password`, `secret`, `clientSecret`, `client_secret`, `apiKey`, `api_key`, `authorization`.

Matching is **case-insensitive**. The masking happens at the display layer (`printer.go`) — raw data remains intact for reporting.

**Configurable** via `.gherkio/config.yaml`:
```yaml
security:
  mask:
    enabled: true
    fields:
      - customField
      - anotherSecret
```
When `fields` is empty, the built-in defaults are used.

### 9. Timing Assertions

Steps can specify a maximum duration:

```yaml
- request:
    method: POST
    url: /auth/login
    ...

  timing:
    max: 500ms
```

- Uses Go duration format: `500ms`, `1s`, `250ms`
- Generates an assertion with path `timing.max`
- Actual duration is always shown inline (both pass and fail)
- Implemented in `executor.go` via `evaluateTiming()`
- Duration is measured per-step from start to completion

### 9a. Request Timeout

Override the default 30-second HTTP client timeout on a per-request basis:

```yaml
- request:
    method: GET
    url: /slow-endpoint
    timeout: 60s
```

- Uses Go duration format: `5s`, `30s`, `1m`, `1m30s`
- Empty or invalid timeout falls back to 30s default
- `0s` means no timeout (unlimited wait)
- Distinct from `timing.max` (which is an assertion, not a client deadline)
- Implemented in `executor.go` in `executeRequest()`

### 10. Failure UX — Contextual Diagnostics

When an assertion fails, the output is designed for debugging, not just pass/fail:

**Path not found** — Instead of a generic "(not found)", shows:
```
✗ response.accessToken exists
    └─ path not found

Available fields:
  - message
  - statusCode
```

**Response body on error** — When any assertion in a step fails, the full response status + body is displayed automatically:
```
Response:
Status: 400

Body:
{
  "message": "Invalid credentials"
}
```

This behavior is implemented in `internal/runner/printer.go`. The `Suggestions` field on `AssertionResult` (populated by `getAvailableFields()` in `executor.go`) drives the available-fields listing.

## Testing Philosophy (from PRD)

- **Declarative-first**: Tests describe behavior, not implementation
- **Readability matters**: Scenarios should be readable after 1-2 years
- **Observability**: Every execution produces structured results (request, response, assertions)
- **Constrained DSL**: No loops, no branching, no arbitrary code in the DSL
- **Assertion-centric**: The assertion engine is "the heart" of Gherkio
- **Capability system** (future): Controlled extensibility via plugins, not inline scripting

## CLI Interface

```
gherkio init                                  # Scaffold .gherkio/ directory
gherkio run                                 # Run all tests in .gherkio/tests/
gherkio run <test-file>                       # Execute a single test scenario
gherkio run <directory>/                      # Run all tests in a subdirectory
gherkio run <test-file> --env <environment>   # Run with specific environment
gherkio run <test-file> --verbose             # Show full request/response payloads
gherkio run <test-file> --report html         # Generate HTML report
gherkio run <test-file> --report json         # Generate JSON report
gherkio run <test-file> --report html,json    # Generate both reports
gherkio run <test-file> --report json --report-raw # Unmasked JSON
gherkio run <test-file> -v                    # Shorthand for --verbose
gherkio run <test-file> --env staging --account alpha   # Run with specific account
gherkio run <test-file> --env staging --all-accounts    # Run against all accounts
gherkio schema                              # Generate JSON Schema for YAML autocomplete
```

Test file resolution order:
1. Absolute path as-is
2. Relative to current working directory
3. Relative to `.gherkio/tests/` in the project root

Project root detection: walks up from cwd looking for `.gherkio/` directory.

### 🔄 Self-Update Rule
**Every change to this codebase MUST also update `llm-map.txt`** if the change affects:
- Project structure (new files, directories, or packages)
- Dependencies (new or removed)
- Architecture or data flow (new execution paths, changed types)
- CLI interface (new commands, flags, or behaviors)
- Key types or their fields
- Design patterns or conventions

This file is the single source of truth for AI context. Keeping it current ensures that every agent working on Gherkio has an accurate mental model of the project without having to re-read the entire codebase.

**Exception**: Cosmetic or trivial changes (typo fixes, minor refactors that don't alter structure/behavior) don't require an update.

- When adding new features, maintain the **declarative DSL philosophy** — no arbitrary code execution in the DSL layer
- Keep the `internal/model/` types clean — they represent the YAML schema
- Keep `internal/runner/` focused on orchestration — break large files into focused ones
- Use the `cmd/` pattern (cobra `RunE` → private function) for new subcommands
- All user-facing output goes through `printer.go` or the cmd layer
- Prefer explicit error wrapping over generic error messages
- When in doubt, check `docs/prd.md` for product philosophy guidance

### 11. Multi-Account Credentials System (RFC-12)

Gherkio supports running the same test scenarios against multiple accounts via a credentials system.

**Credentials file** — Lives at `.gherkio/credentials/<env>.yaml`:

```yaml
accounts:
  alpha:
    username: alpha@test.com
    password: alpha-secret
    role: admin
  beta:
    username: beta@test.com
    password: beta-secret
    role: viewer
```

**CLI flags:**
- `--account <name>` — Run with a specific account
- `--all-accounts` — Run against all accounts in the credentials file

**Variable injection:** Account fields (`username`, `password`, `role`, plus any inline extras) are injected as variables (`$username`, `$password`, `$role`) before step execution. Saved step variables override credential variables.

**Edge cases:**
- No credentials file → test runs normally (no credentials)
- 1 account, no flag → auto-used (zero-config)
- 2+ accounts, no flag → hint printed, runs without credentials
- `--account` with missing file → warning, flag ignored
- `--account` with nonexistent name → error listing available accounts
- Passwords and sensitive credential fields auto-added to mask

**Implementations:**
- `internal/model/credentials.go` — `Credentials` and `Account` structs
- `internal/runner/credentials.go` — `LoadCredentials()`, `CredentialsToVars()`, `GetSensitiveFieldsFromCredentials()`
- `cmd/run.go` — `resolveAccounts()` handles auto-use, multi-account iteration, and per-account masking
- `cmd/init.go` — Creates `.gherkio/credentials/` with a default `local.yaml`

### 12. HTML & JSON Reporting
Gherkio supports generating standalone HTML reports for test runs.
- **Trigger**: via CLI flag `--report html` or `--report json` or `.gherkio/config.yaml` `reports.format: html,json`.
- **Output**: Saved to `.gherkio/reports/latest/report.html` and a timestamped directory.
- **Features**: Includes masked payloads, copyable cURL commands, extracted Request IDs from headers, and inline timing assertion results.
- **Multi-Scenario Grouping**: When running multiple test files (e.g. `gherkio run` with no args or a directory), each scenario is reported as a **separate group** in the report, with its own header, pass/fail stats, and grouped steps. The suite-level summary shows aggregate stats. Each `StepResult` carries `ScenarioName` and `TestFile` to enable this grouping.
- **Report Types**:
  - `internal/report/types.go` — `ReportData` (has both `Steps` for single-scenario and `Scenarios []ScenarioData` for multi-scenario), `ScenarioData`, `ReportStep`, `ReportAssertion`, `ReportConfig`
  - `internal/report/html.go` — `RenderHTML()` for single, `RenderHTMLSuite()` for multi (calls `MapResultsToSuiteReportData()`), shared `renderHTMLTemplate()`
  - `internal/report/json.go` — `RenderJSON()` for single, `RenderJSONSuite()` for multi
  - `internal/report/template.html` — supports both modes via `{{if .Scenarios}}...{{else}}...{{end}}`
- **Implementation**: Uses `html/template` with `//go:embed` to embed `assets/template/report.html` directly into the binary (no external dependencies). Housed in the `internal/report/` package.
