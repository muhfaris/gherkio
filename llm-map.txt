## Project Identity

- **Name**: Gherkio
- **Tagline**: Declarative Integration Testing Platform
- **Language**: Go 1.25.0
- **Module**: `github.com/muhfaris/gherkio`
- **Author**: Faris (muhfaris)
- **Current version**: v0.1.0

### What Gherkio Is

A CLI tool that executes declarative YAML-based integration test scenarios against HTTP APIs. Users describe requests, assertions, and variable extractions in YAML — no imperative code required.

### What Gherkio Is NOT

- A general-purpose programming language
- A unit testing framework
- A browser/E2E testing tool
- A BDD/Gherkin natural language parser

## Architecture & Data Flow

### Execution Flow (`runner.Run()`)

```
Load YAML test file  ──→  Load environment YAML  ──→  For each phase:
    │
    ├── Setup (if defined)
    │   └── 1. Execute setup steps (failure skips main steps, teardown still runs)
    │
    ├── Steps (if setup succeeded)
    │   ├── 1. Interpolate request variables ($var / ${var})
    │   ├── 2. Resolve URL (via env.baseUrl or env.services[].baseUrl)
    │   ├── 3. Execute HTTP request (Wrapped in Retry Loop if `retry` is configured)
    │   ├── 4. Auto-decode JWT from response.token or response.access_token
    │   ├── 5. Run assertions (status + body/JWT matchers)
    │   ├── 6. Extract & save variables (on successful retry or after exhaust)
    │   └── 7. Collect results
    │
    └── Teardown (if defined)
        └── 1. Execute teardown steps (always, even if setup/steps failed)
            - Failures are recorded but don't affect scenario pass/fail
```

## Key Design Patterns & Conventions

### 1. Cobra CLI Pattern

- Root command in `cmd/root.go`
- Subcommands in `cmd/<name>.go` with `init()` registering via `rootCmd.AddCommand()`
- Each subcommand's `RunE` calls a private function (e.g. `runInit()`, `runTest()`)

### 2. Explicit Error Handling

- All errors are wrapped with `fmt.Errorf("context: %w", err)` 
- No panics in production paths
- CLI commands return errors (not `os.Exit`) so cobra handles exit codes

### 3. YAML Model Pattern

- Models use `yaml` struct tags
- `Expect` has a custom `UnmarshalYAML` to handle mixed-type inline fields:
  - `status` → integer field
  - Everything else → `map[string]interface{}` via `,inline`

### 4. Path Syntax (Canonical)

Assertion and save paths follow dot-notation:

| Prefix | Context | Description |
|--------|---------|-------------|
| `body.<field>` | expect / save | Response JSON body field (canonical) |
| `headers.<name>` | expect / save | Response header |
| `status` | expect only | HTTP status code |
| `jwt.<claim>` | expect / save | Decoded JWT claim (auto-decoded from `body.token` or `body.accessToken`) |
| `timing.max` | auto (from `timing:` block) | Step duration must be ≤ max (e.g. `500ms`, `1s`) |
| `timing.duration` | expect only | Total step round-trip latency (e.g. `lte 500ms`, `gt 1s`) |
| `schema` | expect only | Validates full parsed response body against a YAML schema |

**Backward-compatible aliases** (still work but not recommended for new tests):
- `response.<field>` → same as `body.<field>`
- `response.body.<field>` → same as `body.<field>`
- `response.headers.<name>` → same as `headers.<name>`
- Bare `<field>` → fallback, tries response body directly

**Rule of thumb:** In expect, use `body.X`. In save, use `body.X`. Always explicit, never ambiguous.

### 5. Matchers

| Matcher | Behavior |
|---------|----------|
| `exists` | Field must exist (any value) |
| `not exists` | Field must NOT be present (negative assertion) |
| `uuid` | Valid UUID format (v4) |
| `email` | Valid email format |
| `datetime` | Valid RFC3339 / ISO8601 datetime |
| `uri` | Valid URI format (e.g. https://...) |
| `string` | Value is a string type |
| `number` | Value is a numeric type (int, float, json.Number) |
| `boolean` | Value is a boolean type |
| `array` | Value is an array type |
| `object` | Value is an object type (map) |
| `null` | Value is null |
| `true` | Value is boolean true |
| `false` | Value is boolean false |
| `contains <substring>` | String contains substring (case-sensitive) |
| `startsWith <prefix>` | String starts with prefix |
| `endsWith <suffix>` | String ends with suffix |
| `regex <pattern>` | String matches regex pattern |
| `count(path): <N>` | Array has exactly N items (collection matcher). Also: `count(path).gte`, `.gt`, `.lte`, `.lt` for range checks (e.g. `count(body.items).gte: 1` means "has data") |
| `all(path): <matcher>` | Every element in array matches (collection matcher) |
| Literal value (e.g. `admin`, `200`) | Equality comparison (string) |
| `schema: <name>` | Validate full response body against a YAML schema |
| `schema: not <name>` | Response must NOT match schema (negative assertion) |

### 6. Variable Interpolation

- Syntax: `$var` or `${var}` or `${var:default}` or `$accounts.eka.username` or `${randomInt(min,max)}`
- Function-call syntax: `${func(arg1,arg2)}` for parametrized built-in generators (e.g. `${randomInt(1,100)}`). Falls back to normal variable lookup if function name is not recognized.
- Dotted-path syntax: `$accounts.<name>.<field>` navigates nested maps (e.g. all injected credentials)
### 7. Variable Interpolation

- Syntax: `$var` or `${var}` or `${var:default}` or `$accounts.eka.username` or `${randomInt(min,max)}`
- Function-call syntax: `${func(arg1,arg2)}` for parametrized built-in generators (e.g. `${randomInt(1,100)}`). Falls back to normal variable lookup if function name is not recognized.
- Dotted-path syntax: `$accounts.<name>.<field>` navigates nested maps (e.g. all injected credentials)
- Applied to: URL, headers, body (recursive string/map/array)**and save paths** — save paths also support interpolation, so you can use `body.data[$randomInt(0,9)].id` to dynamically pick an array element.
- Resolution (strict): `resolveNestedVar()` in `internal/runner/interpolator.go` splits by `.` and walks the nested map, returns error on undefined
- Resolution (lenient): `resolveNestedPath()` in `internal/converter/curl.go` same navigation but leaves unresolved vars intact — used by cURL converter
- Variables are stored in `map[string]interface{}` and passed between steps
- **Order of precedence** (later overrides earlier): 1. Host Environment variables (prefixed with GHERKIO_) → 2. Credential vars → 3. Step saves → 4. Built-in generators (fresh each step, always overrides for overlapping built-in names)

#### Host Environment Variables
Loaded at the start of a `Run()` or `RunSingleStep()` call from system environment variables starting with the case-sensitive prefix `GHERKIO_`. Any non-prefixed variables (e.g. `PATH`, `USER`) are strictly ignored to prevent credential or context leakage.

#### Built-in Generator Variables
Available in every test run with no setup. Generated once per `Run()` call via `BuiltinVars()` in `internal/runner/builtins.go`:

| Variable | Description | Example |
|----------|-------------|--------|
| `$uuid` | UUID v4 string | `a1b2c3d4-e5f6-4789-abcd-ef1234567890` |
| `$ulid` | ULID (timestamp + random) | `01ARZ3NDEKTSV4RRFFQ69G5FAV` |
| `$randomInt` | Random integer 0–999999. Use `${randomInt(min,max)}` for custom range (e.g. `${randomInt(1,100)}`) | `74291` |
| `$randomEmail` | Random email at @example.com | `user_123456@example.com` |
| `$randomPhone` | Random phone number (defaults to Indonesian format `+6281234567890`). Use `${randomPhone(ISO)}` (e.g. `SG`, `JP`, `FR`) or `${randomPhone(prefix)}` (e.g. `+351`) for global formats. | `+6281234567890` or `+6589012345` |

**Parametrized generators (function-call syntax):** The function syntax (e.g. `${randomInt(min,max)}` or `${randomPhone(countryOrPrefix)}`) is handled by `GetGeneratorFuncs()` in `internal/runner/builtins.go`, which returns a map of generator names to handler functions. The interpolator (`interpolator.go`) detects parenthesized arguments in variable references and dispatches to the appropriate generator. Currently supported:
- `randomInt(min, max)` — Random integer in range [min, max] inclusive.
- `randomPhone(countryOrPrefix)` — Random phone number. Parameter can be a 2-letter ISO country code (supporting 23 countries: ID, SG, MY, PH, TH, VN, JP, KR, IN, US, GB, AU, CA, DE, FR, IT, ES, NL, BR, MX, RU, ZA, SG) or a custom dialing/prefix string (e.g. `+351` or `351`). Falls back to Indonesian format if empty or unrecognized.

**Per-step regeneration:** Built-in variables are regenerated fresh at the start of each step iteration (inside `executeSteps()` in `runner.go`). This means each request in a scenario gets unique values — critical for real QA testing where every API call needs distinct IDs, idempotency keys, or random data.

Within a single step, all occurrences of `$uuid` (URL, headers, body) resolve to the same value. But step 2 will get a different `$uuid` than step1.

**Variable precedence (per step):**
1. Host Environment variables (prefixed with `GHERKIO_`, loaded at start)
2. Credential vars (from account selection or `$accounts`, loaded at start)
3. Step saves from previous steps (override above)
4. Built-in generators (fresh each step, always overrides built-in keys like `$uuid`, `$ulid`, etc.)

Built-in vars also resolve in cURL conversion (`gherkio convert -r`), also regenerated per step.

Example usage:
```yaml
body:
  idempotencyKey: $uuid
  requestId: $ulid
  otpCode: $randomInt
```
- **cURL converter** (`gherkio convert -r`) also resolves `$accounts.<name>.<field>` by loading credentials and injecting all accounts into `vars["accounts"]` in `cmd/convert.go::runReverseConvert()`

### 7. JWT Auto-Decoding

If `response.token` or `response.access_token` exists and is a string, it's automatically decoded (no signature verification) into a `map[string]interface{}` available via `jwt.<claim>` assertions.

### 8. Sensitive Field Masking

When displaying request/response bodies in the console, sensitive field values are automatically masked as `***masked***`.

**Built-in default fields:** `token`, `accessToken`, `access_token`, `refreshToken`, `refresh_token`, `password`, `secret`, `clientSecret`, `client_secret`, `apiKey`, `api_key`, `authorization`.

Matching is **case-insensitive**. The masking happens at the display layer (`printer.go`) — raw data remains intact for reporting.

**Configurable** via `.gherkio/config.yaml`:
```yaml
security:
  mask:
    enabled: true
    fields:
      - customField
      - anotherSecret
```
When `fields` is empty, the built-in defaults are used.

### 9. Timing Assertions

Steps can specify a maximum duration:

```yaml
- request:
    method: POST
    url: /auth/login
    ...

  timing:
    max: 500ms
```

- Uses Go duration format: `500ms`, `1s`, `250ms`
- Generates an assertion with path `timing.max`
- Actual duration is always shown inline (both pass and fail)
- Implemented in `executor.go` via `evaluateTiming()`
- Duration is measured per-step from start to completion

### 9a. Request Timeout

Override the default 30-second HTTP client timeout on a per-request basis:

```yaml
- request:
    method: GET
    url: /slow-endpoint
    timeout: 60s
```

- Uses Go duration format: `5s`, `30s`, `1m`, `1m30s`
- Empty or invalid timeout falls back to 30s default
- `0s` means no timeout (unlimited wait)
- Distinct from `timing.max` (which is an assertion, not a client deadline)
- Implemented in `executor.go` in `executeRequest()`

### 10. Failure UX — Contextual Diagnostics

When an assertion fails, the output is designed for debugging, not just pass/fail:

**Path not found** — Instead of a generic "(not found)", shows:
```
✗ response.accessToken exists
    └─ path not found

Available fields:
  - message
  - statusCode
```

**Response body on error** — When any assertion in a step fails, the full response status + body is displayed automatically:
```
Response:
Status: 400

Body:
{
  "message": "Invalid credentials"
}
```

This behavior is implemented in `internal/runner/printer.go`. The `Suggestions` field on `AssertionResult` (populated by `getAvailableFields()` in `executor.go`) drives the available-fields listing.

## Testing Philosophy (from PRD)

- **Declarative-first**: Tests describe behavior, not implementation
- **Readability matters**: Scenarios should be readable after 1-2 years
- **Observability**: Every execution produces structured results (request, response, assertions)
- **Constrained DSL**: No loops, no branching, no arbitrary code in the DSL
- **Assertion-centric**: The assertion engine is "the heart" of Gherkio
- **Capability system** (future): Controlled extensibility via plugins, not inline scripting

```
gherkio init                                  # Scaffold .gherkio/ directory
gherkio run                                 # Run all tests in .gherkio/tests/
gherkio run <test-file>                       # Execute a single test scenario
gherkio run <directory>/                      # Run all tests in a subdirectory
gherkio run <test-file> --env <environment>   # Run with specific environment
gherkio run <test-file> --verbose             # Show full request/response payloads
gherkio run <test-file> --report html         # Generate HTML report
gherkio run <test-file> --report json         # Generate JSON report
gherkio run <test-file> --report html,json    # Generate both reports
gherkio run <test-file> --report json --report-raw # Unmasked JSON
gherkio run <test-file> -v                    # Shorthand for --verbose
gherkio run <test-file> --env staging --account alpha   # Run with specific account
gherkio run <test-file> --env staging --all-accounts    # Run against all accounts
gherkio run <test-file> --section <section>            # Run ALL steps in a section only (setup, steps, teardown)
gherkio run <test-file> --step <N>                      # Run a single step (0-indexed)
gherkio run <test-file> --step <N> --section <section>  # Run a single step in a specific section
gherkio run <test-file> --line <N>                      # Run the step at a specific line number
gherkio run <test-file> --dry-run                     # Preview execution without HTTP requests
gherkio run <test-file> --tag <tag>                    # Filter tests by tag (AND logic)
gherkio run --parallel <N>                             # Run tests concurrently
gherkio validate                                       # Lint test files statically
gherkio schema                              # Generate JSON Schema for YAML autocomplete
```

Test file resolution order:
1. Absolute path as-is
2. Relative to current working directory
3. Relative to `.gherkio/tests/` in the project root

Project root detection: walks up from cwd looking for `.gherkio/` directory.

- Dependencies (new or removed)

### 11. Multi-Account Credentials System (RFC-12)

#### Namespaced Account Access (`$accounts.<name>.<field>`)

All accounts from the credentials file are automatically injected into a special `$accounts` variable as a nested map. This allows accessing any account's fields directly in test YAML without passing `--account`:

```yaml
steps:
  - request:
      method: POST
      url: /auth/login
      body:
        username: $accounts.eka.username      # → "0000002"
        password: $accounts.eka.password      # → "0000002"

  - request:
      method: GET
      url: /users/me
      headers:
        Authorization: Bearer $token
    expect:
      body.role: $accounts.default.role       # → "user"
```

**How it works:**
- `internal/model/credentials.go` — `Credentials.ToMap()` converts all accounts to `map[string]interface{}`
- `cmd/run.go` calls `ToMap()` after loading credentials and passes the result as `AllAccounts` on `RunConfig`
- `internal/runner/runner.go` injects `vars["accounts"]` in both `Run()` and `RunSingleStep()`
- `internal/runner/interpolator.go` — `resolveNestedVar()` splits dotted paths by `.` and navigates the nested map, supporting syntax like `$accounts.eka.username` or `${accounts.eka.username}`

**Backward compatibility:**
- `$username`, `$password` still work for the selected account (via `CredentialVars`)
- `--account` and `--all-accounts` flags unchanged
- `$accounts.<name>.<field>` is additive — no breaking changes

**Hint suppression:**
When a test file references `$accounts.`, the "N accounts found..." hint is automatically suppressed (the user is already using accounts explicitly). Implemented via `testReferencesAccounts()` in `cmd/run.go` which scans the test YAML for `$accounts.` string.

**MCP Server updates:**
- `gherkio://dsl/spec` resource now documents variable interpolation including `$accounts.<name>.<field>`
- `gherkio://dsl/examples` resource includes a multi-account example using `$accounts`
- `run_test` handler passes `AllAccounts` from `Credentials.ToMap()` so LLM-generated tests using `$accounts` work via MCP
- `run_test` MCP tool has a `section` parameter: when set without `step`, runs ALL steps in that section only (setup/steps/teardown)
- New MCP resources: `gherkio://dsl/matchers` (all assertion matchers with descriptions), `gherkio://dsl/variables` (built-in generator variables), `gherkio://dsl/paths` (canonical assertion/save paths) — exposed as JSON, fully dynamic via `runner.GetMatchersInfo()`, `runner.GetVariableInfo()`, `runner.GetPathInfo()`
- New MCP resource: `gherkio://project/structure` — explains the `.gherkio/` directory layout so LLMs know where to create files
- New MCP tools for LLM self-service: `create_credential`, `update_credential`, `read_credential`, `create_environment`, `update_environment`, `create_schema`, `update_schema`

Gherkio supports running the same test scenarios against multiple accounts via a credentials system.

**Credentials file** — Lives at `.gherkio/credentials/<env>.yaml`:

```yaml
accounts:
  alpha:
    username: alpha@test.com
    password: alpha-secret
    role: admin
  beta:
    username: beta@test.com
    password: beta-secret
    role: viewer
```

**CLI flags:**
- `--account <name>` — Run with a specific account
- `--all-accounts` — Run against all accounts in the credentials file

**Variable injection:** Account fields (`username`, `password`, `role`, plus any inline extras) are injected as variables (`$username`, `$password`, `$role`) before step execution. Saved step variables override credential variables.

**Edge cases:**
- No credentials file → test runs normally (no credentials)
- 1 account, no flag → auto-used (zero-config)
- 2+ accounts, no flag → hint printed, runs without credentials
- `--account` with missing file → warning, flag ignored
- `--account` with nonexistent name → error listing available accounts
- Passwords and sensitive credential fields auto-added to mask

**Implementations:**
- `internal/model/credentials.go` — `Credentials` and `Account` structs
- `internal/runner/credentials.go` — `LoadCredentials()`, `CredentialsToVars()`, `GetSensitiveFieldsFromCredentials()`
- `cmd/run.go` — `resolveAccounts()` handles auto-use, multi-account iteration, and per-account masking
- `cmd/init.go` — Creates `.gherkio/credentials/` with a default `local.yaml`

### 12. HTML & JSON Reporting
Gherkio supports generating standalone HTML reports for test runs.
- **Trigger**: via CLI flag `--report html` or `--report json` or `.gherkio/config.yaml` `reports.format: html,json`.
- **Output**: Saved to `.gherkio/reports/latest/report.html` and a timestamped directory.
- **Features**: Includes masked payloads, copyable cURL commands, extracted Request IDs from headers, and inline timing assertion results.
- **Multi-Scenario Grouping**: When running multiple test files (e.g. `gherkio run` with no args or a directory), each scenario is reported as a **separate group** in the report, with its own header, pass/fail stats, and grouped steps. The suite-level summary shows aggregate stats. Each `StepResult` carries `ScenarioName` and `TestFile` to enable this grouping.
- **Report Types**:
  - `internal/report/types.go` — `ReportData` (has both `Steps` for single-scenario and `Scenarios []ScenarioData` for multi-scenario), `ScenarioData`, `ReportStep`, `ReportAssertion`, `ReportConfig`
  - `internal/report/html.go` — `RenderHTML()` for single, `RenderHTMLSuite()` for multi (calls `MapResultsToSuiteReportData()`), shared `renderHTMLTemplate()`
  - `internal/report/json.go` — `RenderJSON()` for single, `RenderJSONSuite()` for multi
  - `internal/report/template.html` — supports both modes via `{{if .Scenarios}}...{{else}}...{{end}}`
- **Implementation**: Uses `html/template` with `//go:embed` to embed `assets/template/report.html` directly into the binary (no external dependencies). Housed in the `internal/report/` package.

### 1. The Package Dependency & Circular Import Map
To prevent compiler errors, all modifications must respect Gherkio's package architectural hierarchy:
```text
  [cmd] ──> [internal/mcp]
    │             │
    └─── [internal/core/project] ──> [internal/core/teststore]
                   │                             │
                   └─────────── [internal/runner] ──> [internal/model]
```
- **Crucial Rule**: Do not introduce upstream imports. For example, `teststore` must never import `project`. If you need cross-package functionality, delegate parameters upstream in the `cmd/` or `internal/mcp/` handlers.

### 2. The "Stdout vs Stderr" Rule for MCP Actions
- **Crucial Rule**: When writing tools or handlers under `internal/mcp/`, or core execution paths invoked by MCP, NEVER print logs or diagnostics to standard output (`os.Stdout`, `fmt.Println`, or `log.Printf`). 
- **Reason**: Corrupting `stdout` breaks the JSON-RPC communication stream, crashing the MCP environment. 
- **Standard**: Always redirect diagnostic output to standard error (`os.Stderr` or error return channels).

### 3. Quick-Reference CLI ⟷ Core ⟷ MCP Mapping
| Feature | CLI Command | Core Package Path | MCP Tool Name |
| :--- | :--- | :--- | :--- |
| Run Test | `gherkio run` | `internal/runner/engine.go` | `run_test` |
| Validation | `gherkio validate` | `internal/core/project/validate.go` | `validate_workspace` |
| Scaffold | `gherkio init` | `internal/core/project/init.go` | (CLI only) |
| cURL Convert | `gherkio convert` | `internal/core/converter/` | `convert_curl_to_yaml` |

### 4. Dynamic Schema Reference Rule
- **Crucial Rule**: Do not guess or assume Gherkio YAML structures. 
- **Method**: To retrieve the 100% correct JSON Schema for tests, configs, environments, or credentials, query Gherkio's compiler directly:
  - Run the CLI command: `gherkio schema --type <type>` (options: `test`, `config`, `environment`, `credentials`).
  - Or query Gherkio's MCP tools/resources to resolve the exact DSL definitions dynamically.

### 5. Variable Interpolation Precedence
Variable lookup in `internal/runner/interpolator.go` respects this exact sequence:
```text
Host OS Environment Variables (GHERKIO_*)
  └── Credentials (loaded from .gherkio/credentials/ env blocks)
        └── Step Extractions (extracted during steps via `save:`)
              └── Built-in / Parameterized Generators ($uuid, $randomInt)
```

### 6. Sequential Step-Prefixed Variables for LLM-Generated Scenarios
- **Crucial Rule**: When using MCP tools or writing code to generate or update YAML test scenarios (such as `create_test` or `update_test`), you MUST always format your extracted/saved variable names with a numeric prefix corresponding to the step order (e.g. `1-createdOrderId`, `2-authToken`, `3-userId`). 
- **Reason**: This guarantees strict step-level variable isolation, eliminates naming collision risks across multi-step scenarios, and improves developer readability when tracking variable propagation throughout execution logs.
